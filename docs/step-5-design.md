# Step 5 の実装方針（一時）

更新日: 2026-10-27

## 1. 目的と位置付け

本書は、[実装計画](implementation-plan.md)の Step 5（基底展開・座標取得）の採用方針と実装時の判断を記録する一時的な設計メモである。2026-10-27に、今回の範囲に残る推奨案を採用し、同日に実装・検証を完了した。

対象は `qmb-core` の複合基底と、式全体の展開・再展開・座標取得とする。数学的な契約は[基底](design/basis.md)・[複合式](design/composite-expression.md)に従う。外部数値ライブラリの密・疎コンテナへの接続は Step 6 の `qmb-export` が担当する。

確定した API・契約は[基底の設計第8節](design/basis.md#8-実装した公開-api2026-10-27)、検証結果は[実装計画第4.5節](implementation-plan.md#45-段階5の実装検証状況)に反映した。本書は採用判断の記録として保持し、現在の公開契約はこれらの文書を参照する。

## 2. 決定済み：全因子に同じ局所基底を適用する

2026-10-27 に、今回の実装では因子ごとに異なる局所基底を選ばない方針を採用した。初期版の提供範囲にもこの判断を反映する。

- 一回の展開・座標取得では、対象の primitive 型に対応する局所基底を一つ渡し、対象空間の全基本因子へ共通に適用する。
- 状態には `B: Basis<S, C>`、演算子には `B: Basis<O, C>` を使う。同じ基底の型でも、定義パラメータを因子ごとに変える指定は扱わない。
- 所属空間は状態から取得する。演算子の全作用空間は、明示空間を優先し、なければ既存の束縛先を使う。未束縛かつ明示空間のない場合はエラーとし、局所基底から全空間を推論しない。
- 複合基底は、指定した局所基底と空間の因子順序から core が導出する。利用者に別の複合基底オブジェクトの構築を要求しない。
- 因子ごとの基底配列・基底供給 provider・異なる基底型をまとめるための enum や型消去を、今回の API の前提にしない。内部の列挙・番号変換に必要な補助型は別途設計する。

現在の式では、状態・演算子それぞれの primitive 型 S・O が全因子で共通である。ただし、この型の共通性だけで局所基底の共通性が数学的に決まるわけではない。今回の判断は、基底指定を一つに絞り、API と保持情報を簡素にするための提供範囲の決定である。

### 2.1. 複合基底の導出

局所基底を `B = (b_0, ..., b_{m-1})`、対象空間の基本因子数を `n` とすると、複合基底は空間の因子順序に従う `B` の n 重 tensor product とする。

- 基底番号は既存の mixed-radix 規約に従い、右端の因子が最も速く変化する。今回は全因子の radix が同じ `m` となる。
- Grouping は基底要素・座標・順序を変えない。
- 空の tensor product の基底は `{1}`、単因子の基底は指定された局所基底とする。
- 要素数は primitive の `SpanDimension` と因子数から導出する。総要素数や平坦な番号の整数化では overflow を検出し、空間・式の保持に総次元の整数化を必須としない。
- 全基底の一括生成を要求せず、必要な要素・係数を処理する。

例えば二因子の状態に `SzBasis` を指定すると、順序は `Up⊗Up, Up⊗Down, Down⊗Up, Down⊗Down` となる。演算子に `CartesianBasis` を指定すると、両因子に同じ `{I, Sx, Sy, Sz}` を使う。

### 2.2. 再展開との関係

この制限は、一つの複合基底の内部で全因子に同じ局所基底を使うことを意味する。

- 別の呼び出しで異なる基底を指定して再展開することは引き続き扱う。例えば、全因子に `LadderBasis` を適用した式を、全因子に `CartesianBasis` を適用する形で再展開できる。
- 状態基底と演算子基底を同一にする要求ではない。
- 展開結果は通常の式木であり、基底の識別情報や「展開済み」という状態を式へ保持させない。

## 3. 決定済み：Partial trace は future work とする

2026-10-27 に、partial trace を一旦 future work とし、今回の Step 5 の担当範囲と初期版の必須範囲から外す方針を採用した。

- Partial trace の公開 API、遅延節点、残存空間の構築、評価器への接続、および対応するテストは今回の実装対象に含めない。
- 基底展開・座標取得の実装は、partial trace の設計・実装を前提条件にしない。
- 既存の full trace は引き続き提供する。
- Partial trace の数学的契約は[複合式の設計第7節](design/composite-expression.md#7-full-tracepartial-trace-と埋め込み)に将来の実装向けとして保持する。実施時期と具体的な API・内部設計は再開時に決める。

## 4. 決定済み：写像の表現行列は future work とする

2026-10-27 に、写像の表現行列と表現係数に関する事項も future work とし、今回の Step 5 の担当範囲と初期版の必須範囲から外す方針を採用した。

- 写像を指定する共通 API、複数入力、入力ごとの線型性・共役指定、表現係数の成分・列の取得、係数データの保持・再利用、および対応するテストは今回の対象に含めない。
- 今回の座標取得は、一つの状態式・演算子式を指定基底へ展開した係数を対象とする。
- 基底処理と Step 6 の状態・演算子の密・疎 export は、汎用的な写像の表現行列の設計・実装を前提条件にしない。演算子の数値行列への export は Step 6 の範囲として維持する。
- 数学的契約は[写像の表現行列](design/representation-matrix.md)に将来の実装向けとして保持する。実施時期と具体的な API・内部設計は再開時に決める。

## 5. 決定済み：追加依存を導入しない

2026-10-27 に、今回の Step 5 は既存の依存と `core`・`alloc` の機構で実装・検証し、新しい依存を追加しない方針を採用した。

Primitive の展開には既存の `Basis::expand` を使い、その結果を式全体へ拡張して座標を集約する。非正規直交基底もこの展開規則で扱い、汎用 Gram 行列ソルバーや新たな線型代数ライブラリの導入を必要とする設計にしない。`qmb-core` の `no_std + alloc` を維持する。

## 6. 決定済み：式を返す基底展開と集約済み座標の取得を分ける

2026-10-27 に、`expand_in` は既存の式木で基底展開の結果を返し、数値表現への export に使う集約済み座標は別の API で取得する方針を採用した。

- `expand_in` は、指定基底の要素で表した通常の `LocalState`・`LocalOperator`・`State`・`Operator` を返す。専用の展開結果型、基底情報、座標コンテナ、展開済みマーカー、座標のキャッシュを結果に付随させない。
- 同じ基底成分の係数をまとめる既存の契約は維持する。係数の集約に内部の作業領域を使うことと、戻り値として別の表現を追加することは区別する。
- Export 用には、対象式と基底を入力として集約済み座標を取得する独立した API を提供する。展開済み専用型や事前の `expand_in` 呼び出しを前提にしない。
- 集約済み座標では、同じ基底成分への寄与を合計し、重複しない基底番号と係数を対応付ける。基底順序は局所基底の順序と対象空間の因子順序から導出する。
- 単一成分取得と未集約の寄与の遅延列挙を、今回の独立した公開 API の必須項目にしない。内部走査の手段は実装設計で決める。
- 座標取得 API は `coordinates_in`、返却型は `Coordinates` として具体化した。番号と基底情報の受け渡しは第8.1節に記録し、`expand_in` の戻り値にこれらの選択を持ち込まない。

例えば `2(Up⊗Down) + 3(Up⊗Down) − (Down⊗Up)` は、`expand_in` では係数をまとめた通常の状態式として返す。集約済み座標の API では、同じ数学的結果を基底番号と係数の対応として取得し、export 側が別の数値表現へ格納する。

## 7. 維持する既存の契約

- 通常の作用・内積・期待値・trace に、指定基底への展開や完全な数値行列の生成を必須としない。
- 非正規直交基底も扱い、基底要素との内積値と展開座標を区別する。座標は `Basis::expand` の規則から取得する。
- 展開は入力を変更せず、Index・確定した空間・因子順序を保持する。
- `qmb-core` の `no_std + alloc`、操作ごとの型制約、不変な部分式の共有、反復的な評価・破棄を維持する。

## 8. 採用した実装方針

2026-10-27に、今回の範囲に残る以下の推奨案を採用した。Partial trace・写像の表現行列に関する提案、および単一成分取得・未集約の寄与の列挙を独立した公開 API にする提案は、この採用の対象に含めない。

| 対象 | 採用方針 |
| --- | --- |
| 展開・座標取得の API | `expand_in` と独立した `coordinates_in` を提供し、式への再構成と座標取得で内部の係数処理を共有する |
| 座標番号・返却形式 | Coordinates に基底番号列と係数の組を疎に保持する。番号列と、成分ごとに overflow を検出する平坦番号を列挙できる。全基底や密な領域の確保を必須にしない |
| 係数の集約 | 数値的な基底番号をキーに疎に集約し、基底順で返す。近似誤差で成分を捨てず、既存の `LinearCombination` の保持契約を維持する |
| 座標の解釈に必要な情報 | 対象空間・共通局所基底・因子順序を係数列に対応付ける。通常の式木の保持内容とは分ける |
| エラーと能力制約 | 空間不整合・基底番号や展開先の不正・次元 overflow を区別する。Index に `Hash`・`Ord`・`Clone` を一律要求せず、数値能力も操作ごとに要求する |
| 実装順序 | 局所式の展開・座標取得、共通局所基底からの複合処理の順に進める |

### 8.1. 実装で具体化した詳細

上記の採用方針に従い、以下を実装した。

- 局所式・State・Operator に `expand_in(&basis)` と `coordinates_in(&basis)` を提供した。Operator には `expand_in_space(&basis, &ambient)` と `coordinates_in_space(&basis, &ambient)` を提供し、第2節の空間選択に従う。
- `Coordinates<'b, B, C, H = ()>` は基底を借用し、係数を所有する。複合式では `H = HilbertSpace<I>` として選択空間を共有し、局所式では `H = ()` とする。内部の BTreeMap のキーは `Vec<usize>` とし、`entries()` で番号列、`flat_entries()` で検査付きの平坦番号を基底順で取得する。`dimension()` は総要素数を別途検査する。
- `BasisError` に基底要素・番号・列挙の不正、次元 overflow、空間選択のエラーを分けた。内部走査は反復的に行い、式への再構成では局所式ハンドルを共有する。基底の完全性・線型独立性の実行時自動証明は要求しない。
- 複合基底は `HilbertSpace::basis_states`・`basis_operators` で同じ局所基底から必要な要素を遅延列挙する。式の展開・座標取得で全基底要素の列挙を必須にしない。

具体的な型制約、保持特性、エラーの契約は[基底の設計第8節](design/basis.md#8-実装した公開-api2026-10-27)を参照する。

## 9. 検証方針

既存文書の完了条件に従い、以下を検証した。具体的なテスト配置・実行結果と未検証事項は[実装計画第4.5節](implementation-plan.md#45-段階5の実装検証状況)に記録する。

- 一つの局所基底から導出する複合基底の順序、grouping によらない座標、空・単因子、要素数・番号の overflow。
- 式全体の展開・座標集約・係数からの再構成、別の共通局所基底への再展開、入力の不変性。
- `expand_in` の戻り値が既存の式型であり、基底情報や展開済みマーカーなしで通常の演算に使えること。別 API で取得した座標が重複なく集約され、基底順序と対応すること。
- 深い式の基底処理・破棄と、不変な部分構造の共有。
- 非正規直交基底と既存の三次元テスト代数での共通処理、および独立な小規模行列との一致。
- 通常の作用・内積・trace に基底処理を強制しないことと、集約済み座標の取得に全基底・密行列の一括生成を要求しないこと。
