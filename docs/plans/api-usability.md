# API の使いやすさに関する検討事項

作成日: 2026-10-27

## 1. 目的と位置づけ

現行 API を利用する際の典型的な負担と、今後の API 整備で判断すべき論点を整理する。対象は、利用開始から式の構築・評価・数値出力までの流れと、独自の局所代数を実装する拡張経路である。

各項目の「現状」は現行コード・利用例から確認した事実、「検討事項」は使いやすさの観点からの候補である。利用者調査に基づく問題の頻度や重大度は未確認であり、候補の採用、公開名、配置先、実装順序は未決とする。本書は実装済み機能の仕様を変更しない。

利用者からの方針として、import が多少増えることは許容し、型引数の多さと係数型の指定が分散することを優先して検討する。係数型を選ぶ場所を明確にし、その選択を状態・演算子・モデル構築へ引き継げる API を主要な比較対象とする。

数学的契約は [要件](../requirements.md)と [設計文書](../design/)を参照する。State と Operator の整理、grading などの設計課題は [今後の課題](../future-work.md)で管理し、本書では利用者への影響を扱う。

## 2. 検討に使う代表的な利用シナリオ

| シナリオ | 確認する使いやすさ | 現行の参照先 |
| --- | --- | --- |
| 1 因子で状態と演算子を作り、作用・期待値を求める | 型指定、構築、演算の向き、評価の必要性 | [spin-half の crate 利用例](../../crates/qmb-spin-half/src/lib.rs) |
| 2 因子の重ね合わせと相互作用を手で作る | 配置、tensor product、和・積、エラー処理 | [基底展開の利用例](../../examples/src/bin/basis_expansion.rs) |
| Chain 上に Hamiltonian と Neel 状態を作る | Index、幾何と空間の接続、モデル utility、正規化 | [Heisenberg の利用例](../../examples/src/bin/heisenberg.rs) |
| 結果を密・疎の数値コンテナで使う | 基底、出力型指定、メタデータ、所有権 | [Heisenberg の export 部分](../../examples/src/bin/heisenberg.rs) |
| builtin 以外の局所代数・基底を実装する | 必要な trait、数学的契約、実装の最小単位 | [3 準位系のテスト用実装](../../crates/qmb-core/tests/support/three_level.rs) |

便利 API の候補は、これらの利用コードで具体的に比較する。短いコードで書けることに加え、意味を読み取れること、失敗時に修正方法が分かることも評価する。

## 3. 典型的な論点

### 3.1. 利用開始時の依存設定と API の発見

**現状**：workspace は 6 つのライブラリ crate に分かれ、利用例は各 crate を直接 import する。正規化・export は trait の import が必要で、`qmb-export` の `ndarray`・`sprs` は個別の任意 feature である。統合窓口の crate や prelude はない。

**検討事項**：

- 典型的な spin-1/2 の用途で必要な依存設定・feature・import を、どこで案内するか。
- 「メソッドが見つからない」場合に、trait の import 不足と feature 不足を利用者が区別できるか。

import の行数削減は優先課題にしない。prelude や統合窓口の追加は、現時点の整備方針として採用しない。

確認には [workspace の依存設定](../../Cargo.toml)、[examples の依存設定](../../examples/Cargo.toml)、[export の feature](../../crates/qmb-export/Cargo.toml)を使う。

### 3.2. 型引数・型推論・係数の指定（優先課題）

**現状**：局所状態は `LocalState<S, O, C>`、局所演算子は `LocalOperator<O, C>`、複合式にはさらに Index 型 `I` が加わる。primitive 自体は数値精度を持たない。[基底展開の利用例](../../examples/src/bin/basis_expansion.rs)では型別名、[Heisenberg の利用例](../../examples/src/bin/heisenberg.rs)では `Complex<f64>` の明示指定を用いる。係数型・精度の暗黙変換は行わない。

負担は「一つの型を指定する際の型引数の多さ」と「同じ係数型を複数の入口で指定・管理すること」に分けて検討する。現行の例には次の特徴がある。

- 基底展開の例は `LocalState<Ket, Op, Complex<f64>>` と `LocalOperator<Op, Complex<f64>>` の型別名を別々に定義する。同じ代数・係数型であることを利用側が両方の定義で揃えている。
- Heisenberg の例は `neel::<_, Complex<f64>>(...)` で状態の係数型を指定し、期待値の計算で状態と演算子を接続することで Hamiltonian 側の係数型も推論される。すべての構築箇所で明示指定が必須というわけではない。
- `heisenberg(..., 1.0_f64)` の `f64` は結合定数の型であり、式の係数型 `C` を一意には決めない。数値引数の精度と式全体の係数型の選択は区別する。
- `Operator<I, O, C>` 自体は状態型 `S` を持たないため、行列 export では `MatrixArgs::<SpinHalfState, _>` による別の型指定が現れる。これは係数型の再指定とは別の負担である。

**検討事項**：

- builtin の状態型・演算子型の組を毎回指定せずに使える入口を用意できるか。
- 係数型をどこで一度指定すれば、独立した状態・演算子の構築、モデル utility、基底処理へその選択を引き継げるか。
- 後段の期待値計算や戻り値の型注釈に依存せず、構築段階で型が決まる書き方を用意できるか。
- `Complex<f32>`・`Complex<f64>` と任意の係数型を、同じ基本 API で扱えるか。
- 数値リテラルや実数によるスカラー倍をどう案内・補助するか。省略時の型を導入する場合、精度の意図しない固定を招かないか。

比較する候補と、各候補だけでは解決しない点を整理する。いずれも採用未定である。

| 候補 | 改善できること | 確認する点 |
| --- | --- | --- |
| builtin の型別名 | 状態・演算子 primitive の型指定を省ける | 個別の型別名だけでは係数型の指定先が複数残る |
| 代数と係数型を一度選ぶ構築用の型・値 | 同じ選択から状態・演算子・モデルを作れる | 必要な保持情報、既存 API との接続、利用者が定義する代数への適用範囲 |
| 型同士の関連付けやシグネチャの見直し | 重複した型情報を推論・関連型から導ける可能性がある | 任意の状態型・演算子型の対応と、保持・遅延構築に必要な trait 制約への影響 |

係数型の指定回数と、利用者が把握する必要のある型引数の両方で比較する。係数型の短い別名を用意するだけでは、指定箇所の分散は解消しない。また、保持・遅延構築に評価用の能力を要求しない現在の契約との両立を確認する。構築用の入口を検討することは、HilbertSpace や Chain 自体に係数型を持たせる決定を意味しない。

候補の具体的な比較、関連型と共通 constructor を持つ `QuantumSystem` trait、試作による確認結果は [型引数と係数型の指定を集約する API 案](api-type-parameters.md)に記録する。関連型名は `State`・`Operator`・`Coeff` とし、個別 primitive 用メソッドは今回追加しない。製品 API への実装は未実施である。

### 3.3. primitive から式を作るまでの手順

**現状**：状態・演算子は `LocalState::primitive(...)`／`LocalOperator::primitive(...)` で局所式にし、`.at(&factor)?` で配置する。配置先には `HilbertSpace` の葉を渡す。spin-half の局所式専用コンストラクタや primitive から式への `From` 実装はない。

**検討事項**：

- primitive を受け取る共通の `state(...)`・`operator(...)` で構築する。`Up`・`Down`・`Sx`・`Sz` など個別 primitive 用のメソッドは今回追加しない。
- 局所式を作る操作と因子へ配置する操作を、呼び出し側が読み分けられるか。
- 便利な構築経路を追加する場合、Index を新規発行する操作と既存 Index を使う操作をどう明示するか。
- 個別の構築補助と `heisenberg`・`neel` のようなモデル utility の間に、共通して必要な操作があるか。

例として、現在の `LocalState::<Ket, Op, Complex<f64>>::primitive(Ket::Up).at(&factor)?` が、どの部分に利用者の意図を表し、どの部分に反復的な記述を要求しているかを比較する。

### 3.4. Index・Site・Factor・全空間の対応

**現状**：`Chain` は Site ごとの Index 列と境界条件を保持し、`to_space()` は同じ Index を持つ空間を作る。`HilbertSpace` は Index と tensor 構造を保持し、局所代数や次元を保持しない。葉は `children()` などの走査から取得できるが、Index を指定して Factor を返す検索 API はない。モデル utility は呼び出し側の空間と Chain の対応を検証する。

**検討事項**：

- Chain の特定 Site に局所演算子を置く場合、Factor への接続をどこまで補助するか。
- 空間を直接作る利用者と Chain を使う利用者で、配置操作を共通して理解できるか。
- Site 順序、Site 内の Index 順序、全空間の因子順序、grouping の違いをどう提示するか。
- 接続補助を追加する場合、同じ自由度の Index を維持し、既存の因子順序・grouping を尊重できるか。

現行契約は [空間の実装](../../crates/qmb-core/src/space.rs)、[Chain から空間への変換](../../crates/qmb-geometry/src/space.rs)、[モデル utility](../../crates/qmb-spin-half/src/utility.rs)を参照する。

モデル構築 API は、`xyz`・`heisenberg`・`neel` を `SpinHalf<C>` の関連関数とし、Chain と Site 順の局所空間列を受け取る方針とする。入力要素は葉に限定せず、そこから実際の葉を取得して `at()` に渡す。全空間の引数は不要で、モデルが局所空間を列順に tensor して構築する。具体的な引数・契約は [型引数と係数型の指定を集約する API 案の第4.3節](api-type-parameters.md)に記録する。

Chain と HilbertSpace の責任分担は、[接続・保持構造の検討](space-geometry-connection.md)に記録する。Chain はサイト数と境界条件だけを保持する方針で合意し、外部の Factor 列を受け取る近接ペア補助を設ける。Factor・配置・空間は利用側で管理する。製品実装は未変更である。

### 3.5. 配置と束縛、作用空間の選択

**現状**：`State` は常に所属空間を持つ。`Operator` は配置された式と任意の全作用空間を持つ。`.at(...)` は未束縛の演算子を作り、`.bind(...)` は明示した空間へ束縛・再束縛する。作用では「明示空間 → 既存の束縛 → 状態の空間」の順に選択する。演算子の和・積は未束縛の入力を含むと未束縛になり、全入力が束縛済みの場合は互換性を検証する。

**検討事項**：

- 配置先と、作用しない因子も含めた全作用空間の違いを、メソッド名・型・説明から理解できるか。
- 束縛情報が合成時に失われる条件や、明示空間が既存束縛を上書きする意味を予測できるか。
- `trace()`・行列 export には全作用空間が必要で、状態への作用には状態の空間を利用できる違いをどう案内するか。
- 型で未束縛・束縛済みを区別する案と、現在の単一型を維持する案に、どのような使い勝手・互換性の差があるか。

空間の選択は計算結果の意味に関わるため、手順の削減と併せて、利用者が選択内容を確認できることを評価する。[現行の配置・束縛の実装](../../crates/qmb-core/src/expr/composite.rs)を比較の基準とする。

### 3.6. 演算子構文・名前付きメソッド・所有権

**現状**：局所式の `+`・`*` は式を直接返し、複合式の和・積・作用は空間を検証して `Result` を返す。複合式の名前付きメソッド `.add(...)`・`.product(...)`・`.act(...)` は共有借用を受ける。演算子構文は所有値・借用の組み合わせに対応する。`.act(...)` は状態側のメソッドであり、`psi.act(&op)` は `op * psi` を意味する。tensor product は名前付き操作で表す。

**検討事項**：

- 連続する和・積で `?` と括弧が増える場合、`sum`・`product_all` などを含め、どの書き方を基本例にするか。
- 演算子積と tensor product、作用の向き、右側から作用する積の順序を読み違えにくいか。
- 中間式を再利用する際、借用と `Clone` による共有を自然に使えるか。
- 任意の係数には `.scaled(c)` と右スカラー倍、標準の `Complex<f32>`・`Complex<f64>` には左スカラー倍もある、という対応範囲をどう示すか。

式の短さだけでなく、構築時にどの失敗を検出するかを維持して比較する。[演算子構文の実装](../../crates/qmb-core/src/expr/operators.rs)を参照する。

### 3.7. 遅延構築・評価・簡約の意味

**現状**：式は不変節点を `Arc` で共有する。状態の `evaluate()` は遅延された作用を処理し、通常の評価では重複項・零係数を保持する。内積・期待値は必要な評価を内部で行う。基底展開・座標取得では同じ基底成分を集約し、厳密な零を除く。近似的な零判定は行わない。演算子には状態と同じ公開 `evaluate()` はなく、trace・基底展開・状態への作用などを通じて計算する。

**検討事項**：

- 明示的な `evaluate()` が必要な場面と、計算メソッドへ直接渡せる場面を区別できるか。
- 評価、基底展開、同類項の集約、数学的な零判定を同じ操作と誤認しないか。
- 状態と演算子で提供する操作が異なる理由を、利用者の目的に沿って説明できるか。
- 計算量・メモリ使用が大きくなる操作を事前に把握できるか。共有は評価結果のキャッシュを意味しないことを伝えられるか。

式の表示・構造比較は [延期した機能](../future-work.md)である。診断のために必要な観測手段を検討する場合は、追加範囲を明示する。

### 3.8. 基底展開・座標・数値 export の選択

**現状**：`expand_in()` は通常の式、`coordinates_in()` は基底を借用する疎な座標データを返す。演算子基底に対する展開係数と、状態基底に対する作用行列は別の対象である。数値出力は `Export` trait に集約され、出力先は戻り値の型で指定する。行列では状態型と基底を `MatrixArgs` で指定する。`Exported` はデータと解釈用メタデータを保持し、基底の借用は結果にも残る。

**検討事項**：

- 式の展開、疎な係数の取得、数値ベクトル・行列の取得から、目的に合う入口を選べるか。
- 出力型の注釈や `MatrixArgs::<SpinHalfState, _>` をどこまで補助するか。名前付きの出力メソッドを追加する価値があるか。
- export 前の明示的な基底展開が必須ではないことを、利用例で伝えられるか。
- 因子順序、右端が最速で変化する基底順序、密行列の row-major 格納順序を区別できるか。
- 結果の基底借用と空間の共有、`data()`・`into_data()`・`into_parts()` の使い分けを理解できるか。
- 非正規直交基底では、座標の単純な共役内積が物理的な内積になるとは限らないことを説明できるか。

疎な座標は総次元が `usize` に収まらなくても扱える場合がある一方、数値コンテナへの出力には寸法・格納量の制約がある。[基底の設計](../design/basis.md)と [export の設計](../design/export.md)を参照する。

### 3.9. エラーと診断の分かりやすさ

**現状**：空間・配置・基底・正規化・export でエラー型が分かれる。Index 重複、因子ではない配置先、不整合な空間、未束縛の演算子、零ノルム、寸法や格納量の overflow などを区別する。`ExpressionError::MissingIndex`・`IncompatibleSpaces` 自体は、対象の Index や期待する順序を保持しない。

**検討事項**：

- エラーから、どの操作・入力が失敗したか、どう修正するかを特定できるか。
- Index や空間の情報を診断へ加える場合、ジェネリックな Index に一律の `Debug`・`Display`・`Clone` 制約を課さずに提供できるか。
- 高水準の利用では `?` でまとめて処理でき、詳細な処理では元のエラーを識別できるか。
- 型不一致などのコンパイルエラーと、空間不整合などの実行時エラーを、利用例でそれぞれ説明できるか。

エラーの情報量と型制約・互換性への影響を一緒に検討する。

### 3.10. ドキュメントと拡張経路

**現状**：利用例、rustdoc、要件・設計文書は存在するが、リポジトリ直下の README はない。独自代数は個別の能力 trait と `Basis` を実装でき、全能力を一括要求する primitive trait はない。3 準位系と非正規直交基底を使うテストが、builtin 以外の利用を検証している。

**検討事項**：

- 初回利用の最短例、手作業のモデル構築、既存 utility の利用、数値出力へ段階的に進める導線があるか。
- trait ごとに必要となる場面と、実装が守る数学的法則を見つけられるか。
- 独自代数の最小例を、テスト内の実装から利用者向けの資料へ整理する価値があるか。
- 基本利用者向けの便利 API と、任意の Index・primitive・係数を使う拡張 API の関係を説明できるか。
- 設計変更の履歴と現行仕様を区別し、利用者が古い前提を採用しないようにできるか。

## 4. API 候補を比較する際の確認項目

具体的な API 案ごとに、次を記録する。以下は今後の判断基準であり、実施済みの検証結果ではない。

1. **対象シナリオと改善する負担**：利用コードの変更前後を示し、省ける知識・型指定・反復操作を説明する。優先課題では、係数型の選択箇所、同じ型情報の繰り返し、後段の処理に依存する型推論を比較する。import の行数削減は主な評価指標にしない。
2. **数学的な意味**：Index の同一性、因子順序、作用空間、係数精度、正規化の有無が読み取れることを確認する。
3. **抽象性と所有権**：独自の Index・代数・係数、非 `Clone` の保持要素、不変な式の共有を必要以上に制限しないか確認する。
4. **失敗時の体験**：不正な配置、空間不整合、型推論不足などの例で、原因と修正方法が分かるか比較する。
5. **配置先と互換性**：crate・feature・依存関係、`no_std`、既存 API への影響、既存の上位設計課題との関係を記録する。
6. **検証方法**：実行可能な利用例、必要な回帰テスト、適切な feature 構成でのビルドを選ぶ。記述量だけで使いやすさを判断しない。

最初は、局所状態・局所演算子を別々に作る例と、Heisenberg・Neel を構築する例で、型引数と係数型の指定方法を比較する。その後、2 因子の式、Chain の特定 Site への配置、密・疎 export まで同じ選択を引き継げるかを確認する。
