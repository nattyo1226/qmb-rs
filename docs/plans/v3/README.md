# v3 に向けた実装案

作成日: 2026-10-30
更新日: 2026-10-31

v3 への更新の対象は以下の4項目とする。各項目の設計状況と採否は、以下および専用文書で管理する。

## 式木表示のカスタムフォーマット

`println!`・`format!` で式木を読みやすく表示できるよう、カスタムのフォーマット実装を検討する。

- `Display` による数式風の表示、`Debug` による構造表示、表示用ラッパーの役割を整理する。公開 API と具体的な書式は未確定とする。
- 和・積・係数・作用・随伴などの節点を区別し、演算の優先順位と括弧、因子順序、Index の表示方法を定める。必要に応じてインデント付きの複数行表示も検討する。
- 表示対象は保持している式木とし、表示のための暗黙の評価・展開・簡約は行わない。
- primitive・係数・Index に必要な表示能力は、表示 API の利用時に要求する。式の構築・評価に一律の `Display`・`Debug` 制約を追加しない。

検証では、入れ子の和・積、非可換な積、複素係数、零・単位元などの表示を確認し、括弧や順序が式の意味を誤って伝えないことを確かめる。

[今後の課題にある式の構造表示 API](../../future-work.md#2-延期した機能と検討事項)を具体化する候補として扱う。

## プロジェクトルートの README とライセンスファイル

プロジェクトルートに `README.md` とライセンスファイルを整備する。

- `README.md` には、プロジェクトの目的・提供機能、crate の構成、依存設定と feature、最小の利用例、examples・設計文書へのリンク、開発時のビルド・検証方法をまとめる。
- 実装済みの機能と将来の計画を区別し、利用例やコマンドは現行の公開 API・リポジトリ構成と一致させる。
- 採用ライセンス、著作権者表記、適用範囲を確定したうえで、対応するライセンスファイルを配置する。採用ライセンスは現時点では未定とする。
- ライセンス確定後、README の案内と workspace・各 crate の Cargo メタデータを整合させる。

検証では、README 内のリンク・利用例・コマンドと、ライセンスファイル・Cargo メタデータの対応を確認する。

## GitHub Actions の workflow 整備

`.github/workflows/` に継続的な検証のための workflow を整備する。現時点では同ディレクトリは存在しない。

- pull request・push 時に、format、Clippy、ビルド・テスト（doc test を含む）、ドキュメント生成を実行する。
- default feature 無効・全 feature 有効に加え、`qmb-export` の backend ごとの feature 構成を確認する。
- MSRV でのビルド・テストと、`no_std + alloc` 対応 crate の専用 target でのビルドを検討し、[未実施の検証](../../future-work.md#3-未実施の検証と性能)を補う。
- 対象ブランチ・OS・Rust toolchain、ジョブ分割、依存キャッシュ、実行時間を整理し、ローカルの検証手順と README の案内を一致させる。

具体的な workflow 構成は未確定とする。導入時には GitHub Actions 上での実行結果を確認し、実施できた検証と残る制約を記録する。

## 3体以上の相互作用に対応する関係の列挙

**設計採用済み・本体未実装（2026-10-31）**。Geometry・Relation<G>・SiteMapper・MappedGroup による構成を採用する。Site 数の取得名は num_sites とする。

最近接のペアに限定された幾何の列挙 API を拡張し、3体以上の相互作用の構築に使えるようにする。旧 `NearestNeighborRelation` は撤去済みだが、現在の `Chain::nn_site_pairs()` と関連する接続 API も2要素のペアを返すため、多体の組を直接列挙できない。

- 「高々 K Site に作用する Pauli string をすべて構築する」を代表的な利用例とする。関係の組を返すだけで終わらず、局所演算子の選択から式構築までを、体数ごとの個別実装や不要に多い trait bound なしで記述できるか確認する。
- 3 Site・4 Site など、相互作用に参加する任意個数の Site を一つの組として列挙する仕組みを検討する。連続する Site の組を出す方法と、一般の多体関係へ拡張する範囲を整理する。
- 将来の正方格子における方向付きの列・中心付き近傍なども扱えるよう、幾何ごとの関係定義と中心・方向の情報保持を検討する。正方格子自体の実装は、この v3 の範囲には追加しない。
- Relation<G> の Group は AsRef<[usize]> を満たす。固定長配列や有効長付きの SiteGroup<CAP> などを使い、外部列への SiteMapper と借用結果の MappedGroup を提供する。
- open／periodic での境界の扱い、Site 数が相互作用の体数より少ない場合、同一 Site の再出現、組の重複、列挙順序を定める。組内の順序が演算子積や graded な符号に関わるため、順序の保持と重複除去の規約を明示する。
- 複数葉の標準操作は MappedGroup の leaves_cartesian・leaves_zip とし、combine_leaves(FnOnce) を共通入口にする。空 Site の位置を保ち、入力列長を検証する。Index の複製・再発行や、空間の暗黙の並べ替えは行わない。
- 既存の2体相互作用の列挙・モデル構築との互換性と移行方法を検討する。多体の組から既存の式構築 API で相互作用項を構築し、geometry に局所代数固有の評価処理を加えない。

検証では、3体・4体の組を open／periodic と小さい Site 数で独立な期待列と比較する。重複・順序・借用先を確認し、組から構築した多体相互作用が手作業で構築した式と一致すること、および既存の2体モデルの結果が維持されることを確認する。

現行の契約は[Chain・Site と自由度の配置](../../design/geometry.md)を参照する。

具体的な設計の検討は[多体相互作用の関係列挙](multi-site-relations.md)に記録する。
採用した設計と移行方針は[幾何・Relation・space 列挙の統合設計](geometry-refactoring.md)を参照する。
