# リファクタリングの整理メモ（一時）

更新日: 2026-10-27

## 1. 目的と位置づけ

本書は、未実施の設計検討と検証事項を記録する。初期版の機能実装は[実装計画](implementation-plan.md)に従い、以下の設計検討の完了を前提条件にしない。

## 2. Operator と State の整理

**状態（2026-10-26）**：検討事項が多いため、設計の検討と、それに基づくリファクタリングを初期版実装後に延期する。初期版では現行の State／Operator の分離を維持し、本項の結論を初期版実装の前提条件にしない。以下の論点は再開時のために保持する。

**目的**：操作的量子論の枠組みで両者を一般の演算子の特別な形として扱えるかを検討し、数学的意味と API の対応を決める。

**現状**：State は ket であり、`ℂ→H` として始域・終域を参照できる。束縛済み Operator は `H→H` として参照できる。ただし、局所・複合それぞれに状態用と演算子用の式木・評価処理があり、一般の `U→V` の写像を表す型はない。

**決めること**：

- 「一般の演算子」が表す数学的対象と、今回扱う状態の意味。Ket、密度演算子、量子操作を同じ対象として扱う前提を置かない。
- 合成、tensor product、随伴、内積、trace、zero・identity を始域・終域とどう対応付けるか。
- 数学的な共通化を公開型、内部表現、共通処理のどこまで反映するか。数学的に整理できることと、公開型を統合することは別に判断する。
- 未束縛の配置式と、始域・終域が確定した写像の関係をどう表すか。

**依存関係**：本項の再開時に空間・幾何との境界を再確認し、型と評価器の統合を伴う実装は、責任分担が定まってから範囲を決める。Grading の情報保持・API の具体化とは独立に検討する。

**完了条件**：採用する数学的対象、対応する API、共通化する範囲、別に維持する範囲を理由とともに記録する。統合を採用しない結論も含む。

## 3. Grading の情報保持と API

**実施時期（2026-10-26の判断）**：後続の fermion 系の実装に合わせて具体化する。

Tensor の積の種類と状態・演算子成分の parity を区別し、どの情報を空間・primitive・合成則が担うかを、既存の graded 演算の数学的契約と具体的な実装要件を踏まえて決める。ToSpace で Grading に必要な情報を渡す方法も、この時点で具体化する。

検討時は[Hilbert 空間の設計](design/hilbert-space.md)、[複合式の数学的契約](design/composite-expression.md)、[ToSpace の契約](design/geometry.md#61-空間への変換能力-tospace)に従う。
